每次新开对话，都像是一次失忆重启。你需要像带新实习生一样，重新把项目规范、技术栈、历史避坑指南喂给它。这种**上下文割裂**，让 AI 始终停留在“问答工具”的阶段，而无法成为真正懂项目的“协作者”。

## 痛点解析：为什么 AI 总是“记不住”？

在现有的 LLM 交互模型中，AI 的记忆本质上是一种**无状态的滑动窗口**。模型只能“记住”当前上下文窗口（Context Window）内的 Token。一旦开启新 Topic，历史对话被清空，AI 对你项目的认知也随之归零。

即使部分工具引入了长文本处理或全局 Prompt 注入，也面临着几个致命问题：
1. **信息淹没**：把所有文档塞进 Prompt，导致 Token 消耗激增，且模型注意力被稀释，关键指令往往被忽略。
2. **缺乏结构化**：AI 对项目的认知是一堆扁平的对话文本，没有形成“规范-决策-反模式”的结构化知识图谱。
3. **无法跨会话沉淀**：昨天踩过的坑，今天换个会话继续踩。

## VTJ.PRO 的破局之道：项目级记忆系统

VTJ.PRO v2.7.1 的核心突破在于引入了**跨 Topic 持久化的记忆机制**。它不再依赖单纯的对话历史，而是为项目建立了一个独立的“海马体”。

### 1. 结构化记忆的提取与存储

当你在与 VTJ.PRO 的 Agent 对话时，系统会在后台进行异步的记忆抽取。它将对话中的非结构化信息提炼为结构化的知识节点，分为三大核心类目：
- **项目规范**：如代码风格、目录结构、命名约束。
- **技术决策**：如为何选择 Redux 而非 Zustand、为何采用 CQRS 架构。
- **避坑规则**：如特定的第三方库版本冲突、已知的 API 陷阱。

### 2. 跨 Topic 持久化与动态召回

新开一个 Topic 时，Agent 不再是一张白纸。VTJ.PRO 的记忆系统会通过一个轻量级的检索器，根据当前 Topic 的意图，从向量数据库中动态召回相关的记忆节点，并将其作为隐式上下文注入 LLM 的系统提示词中。

这意味着，当你在周一的会话中确立了“所有网络请求必须经过统一的拦截器处理”这一规范，到了周三的另一个会话中，当你让 AI 生成一个新的登录接口时，它会自动应用这一规范，无需你重复说明。

### 3. 记忆的演进与冲突消解

项目是演进的，记忆也是。如果早期定下的技术决策在后期被推翻，VTJ.PRO 的记忆系统支持记忆的版本控制和软删除。当检测到新旧记忆冲突时，Agent 会主动向用户确认，并更新知识图谱，确保 AI 的认知始终与项目最新状态对齐。

## 系统架构：从“无状态调用”到“有状态协作”

实现这一系统，VTJ.PRO 在架构上进行了深度改造，主要分为三个阶段：

1. **记忆感知层**：在用户与 LLM 的交互流中，插入异步的 Memory Extractor。它不阻塞主流程，利用边缘模型快速判断对话中是否包含值得持久化的项目知识。
2. **记忆管理中台**：采用混合检索架构（BM25 + 向量检索）。结构化的规范与决策存入关系型数据库，而自然语言描述的上下文则嵌入向量数据库。
3. **上下文注入层**：在 LLM 生成代码前，根据用户的 Prompt 进行意图识别，召回 Top-K 最相关的项目记忆，拼装进 System Prompt。

```go
// 伪代码展示记忆召回逻辑
func (a *Agent) buildSystemPrompt(ctx context.Context, userQuery string) string {
    // 1. 意图识别与记忆召回
    memories := a.MemoryStore.Recall(ctx, userQuery, 5)
    
    // 2. 拼装结构化记忆上下文
    var memoryContext strings.Builder
    memoryContext.WriteString("【项目记忆上下文】\n")
    for _, m := range memories {
        memoryContext.WriteString(fmt.Sprintf("- [%s] %s\n", m.Type, m.Content))
    }

    // 3. 注入最终 System Prompt
    return a.BaseSystemPrompt + "\n" + memoryContext.String()
}
```
